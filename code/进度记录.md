## 2. 环境约束（踩过的坑，务必遵守）

- 机器只有 **8 GB RAM、纯 CPU**。**绝对不要并发跑两个训练**，已经 OOM 两次。
- 必须设线程数，否则 OpenBLAS 在第二个进程会报内存分配失败。四个变量都要设：
  `PYTHONIOENCODING=utf-8`、`OPENBLAS_NUM_THREADS=4`、`OMP_NUM_THREADS=4`、`MKL_NUM_THREADS=4`。
- **PowerShell 5.1 编码坑**：无 BOM 的 UTF-8 `.ps1` 会按 ANSI 解码，中文路径被搞乱
  （`FCNTM完整代码` 变成一堆问号）。写 `.ps1` 一律用 `$PSScriptRoot`，别写中文字面路径。
- 写文本文件用单引号 here-string（`@'` 开头、`'@` 单独成行结尾）配合
  `Set-Content -Encoding UTF8`，会带 BOM，中文正常。
  **注意**：如果内容里本身有行首的 here-string 结束标记，会把外层字符串提前截断，
  文档里别直接贴这种代码块。
- **后台启动 python 必须用绝对路径**：`Start-Process -FilePath 'python'` 会**静默失败**
  （日志文件建了、但子进程根本没起来）。改用 `(Get-Command python).Source`。
- 交互式会话被中断后，它启动的 python 子进程**会变成孤儿存活**，但 stdout 管道已断，
  会在第一次 print 时 BrokenPipe 崩掉且不产出 CSV → 必须手动 `Stop-Process` 结束它。

## 6. 关键结果

### 6.1 收敛：250 epoch 的旧数字是欠训练的（结论已确立）

GitHub，FC-NTM beta，lr=5e-4：

| seed | 250ep best_epoch | 250ep CV | 250ep NPMI | 800ep best_epoch | 800ep CV | 800ep NPMI | 800ep UMass |
|---|---|---|---|---|---|---|---|
| 11 | 250（顶上限） | 0.4914 | −0.0776 | 694 | **0.5668** | **+0.1392** | −9.45 |
| 23 | 207 | 0.5516 | −0.1585 | 800（仍顶上限） | 0.4988 | +0.0052 | −11.21 |

对照基线：BTM NPMI = 0.0605（seed11）/ 0.1329（seed23）；LDA NPMI = 0.0712 / 0.0230。

**含义**：之前"FC-NTM 的 NPMI 大幅落后 BTM"主要是**欠训练假象**，不是本质缺陷。
但 UMass 仍然明显更差，且 seed 23 到 800 epoch 还在改善（未收敛）。

lr 探针（GitHub seed 11，max 1200 epoch）：

- `lr=2e-3` 得到 best_epoch=197、epochs_run=347、**early_stopped=True**（173s），
  但质量更差：CV 0.4318 / NPMI −0.1114。
- 所以**不能用大 lr 图快**；要收敛就得 lr=5e-4 配长预算（1200~2000 epoch）。

### 6.2 `strata` 实验失效（不能当作负结论）

`task_strata` 想把文档按"背景能否被摘要预测"分两层，检验增益是否集中在互补文档上。
诊断发现划分本身不成立：

- GitHub：per-doc R² 中位数 −0.092，且有长尾到 **−620** 的退化样本；
  且"低可预测性"层的 body 平均 **50.1** token，"高可预测性"层 **73.7** token。
  也就是说，这个划分抓的是**文档长度和退化样本**，不是字段互补性。
- AG News：title 平均只有 **2.8 个词**，R² 中位数 0.013、分布很窄，
  中位切分切出来的两层几乎没有区别。

而且训练结果的方向也不支持假设：

| 语料 | 互补层增益 | 冗余层增益 |
|---|---|---|
| GitHub | +65%（0.0263→0.0434） | **+220%**（0.0176→0.0562） |
| AG News | +21%（0.0201→0.0243） | −6%（0.0267→0.0250） |

**结论：这个实验设计没有测到它想测的东西，论文里必须说明其失效，
不能当成"互补性假设被否定"的证据。**

### 6.3 互补性度量工具：**有效**（附一次自我纠错）

我中途一度判断"工具坏了"，**那是我自己的实验 bug**：只改了 train 没改 test，
导致 ridge 在 train 上学到恒等映射、到 test 上灾难性外推。修正为 train/test 同步改造后：

| 条件 | R2(sm→bg) | R2(bg→sm) | cca_mean_r2 |
|---|---|---|---|
| 标题 = 正文完整拷贝（构造上最大冗余） | +1.000 | +1.000 | **1.0000** |
| 标题跨文档打乱（构造上无关联） | −0.769 | −0.118 | **≈0.000** |
| GitHub 原始 | −0.346 | −0.018 | **0.0691** |
| AG News 原始 | +0.078 | +0.035 | **0.1252** |

**上界和下界都对，说明 `field_redundancy.py` 的度量是可靠的**，
可以作为论文里的互补性指标。
（注意：表面词重叠 jaccard 之类**不能**区分这两个语料，别用。）

### 6.4 受控冗余度旋钮 `mix_fields`

做法：把摘要中比例 `rho` 的 token 替换成该文档正文的**开头若干 token 逐字拷贝**。
`rho=0` 保持原样，`rho=1` 时标题完全来自正文（即 AG News 那种"导语复述标题"的结构）。

| rho | 0.00 | 0.25 | 0.50 | 0.75 | 1.00 | 单调? |
|---|---|---|---|---|---|---|
| AG News CCA | 0.125 | 0.166 | 0.186 | 0.216 | 0.271 | **✓ 单调升** |
| GitHub CCA | 0.069 | 0.053 | 0.052 | 0.061 | 0.060 | ✗ 基本不动 |

**结论**：旋钮在 AG News 上有效，在 GitHub 上无效。
原因推测：GitHub 正文开头是 issue 模板样板文字（"Steps to reproduce" 之类），
前缀拷贝不携带正文信息；且 GitHub 标题仅约 5 个词，能拷贝的容量太小。
→ 需要改成「用正文**高频词**做摘要」而不是前缀，才可能两个语料都单调。

**已废弃的一版**：随机从正文抽 token 填充。方向是**反的**——
给定正文后随机子采样仍然不可预测，等于注入噪声而非共享内容，
反而降低跨视图 R²（GitHub 0.069→0.030）。别再用。

1. **800 epoch 消融跑完了**（`outputs/small/ablation_github_ep800.csv`）。

   |---|---|---|---|
   | full | 0.491 / 0.552 | 0.567 / 0.499 | +0.139 / +0.005 |
   | no-cross | 0.561 / 0.513 | 0.481 / 0.564 | +0.090 / −0.213 |

2. **「融合 θ 从未被训练」这个洞是真的**：`gate` 的 `fusion_logit` 因为
   该参数从不进损失，永远是 sigmoid(0)=0.5（这也是变体扫描里 gate 与 recon2
   逐位相同的原因）。现已修好，并且 `fusion_mode="gate"` 实测从 0.5 学到 0.619。

**变体对比（GitHub 小规模，K=20，800ep，种子 11/23/37，β 读出）：**

| 变体 | CV | NPMI | ΔCV vs base | 跨字段召回 |
|---|---|---|---|---|
| base | 0.533±0.020 | 0.054±0.048 | — | 0.066 |
| **gate** | **0.575±0.033** | 0.105±0.049 | **+0.042 (2/3)** | 0.065 |
| **fused** | 0.570±0.036 | **0.120±0.028** | +0.037 (2/3) | 0.064 |
| prior（可学习缺失先验） | 0.570±0.081 | 0.055±0.035 | +0.037 (2/3) | 0.063 |
| autow（按长度配平权重） | 0.471±0.052 | −0.048 | −0.051 (0/2) | 0.061 |
| token（per-token 重建） | 0.437 | −0.165 | −0.088 | 0.061 |
| excl / excl2（排他性） | 0.525 / 0.498 | 0.017 / 0.085 | ±0.000 / −0.020 | 0.078 / 0.072 |

**三条硬结论：**

- 训练融合表示（fused/gate）是唯一稳定有效的改动，但**只改善 β 读出**；
  对 cTFIDF 读出（ΔCV ±0.004）与跨字段召回（Δ −0.003）**中性**。
  → 论文主打的 cTFIDF 数字不会因此变好。
- **排他性正则在数值上完全无效**：对 β 的梯度比重建梯度小约 6 个数量级，

  要改必须改解码器输出形式。
- **autow / token 有害**，别再试。长字段主导重建损失在这两个语料上其实是有用的，

### 13.7 权重扫描 + "门控不可单独训练"的证明

**先证伪了一个本来打算跑的对照**：原计划补"只训练门控、不加融合重构项"这一正交臂，
读代码后发现它在本文的参数化下是**退化的**——`fusion_logit` 只在 `fusion_mode="gate"` 时
创建、初值为 0（$\operatorname{sigmoid}(0)=0.5$），而 `FCNTM.train_step` 里唯一的
`self.fuse(...)` 调用位于 `if self.fused_recon:` 分支内部（另一处在 `encode_doc_theta`，
只用于推理）。去掉融合重构项，门控拿不到任何梯度、恒为 0.5，模型精确退化为均值融合。
论文已把这条写成"该正交组合并不存在"，不再把它列为"未做的对照"。

| 1.0 | 0.716$\pm$0.012 | 0.246$\pm$0.026 | 0.723$\pm$0.012 | 0.277$\pm$0.018 |

三点结论（论文新增 5.9 节 + 表 8）：$\lambda_f=0.25$ 太小（cTFIDF 几乎与不训练融合相同，
